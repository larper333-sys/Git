# Шпаргалка по Git (Ветвление и слияние)

На этой лекции мы изучили ветвление и переход между ветвями. В прошлый раз мы научились сохранять правки (`git commit`), в том числе создавать несколько версий сайта.

## Основные команды

*   `git log` — вызовы списков действий и сохранений.
*   `git init` — создать репозиторий в папке на локальной машине.
*   `git add` — отслеживать добавленные файлы.
*   `git commit + комментарий` — сохранять текущее состояние.
*   `git diff` — показать разницу между версиями.
*   `git checkout` — переключаться между разными версиями.

## Важные правила работы с файлами

*   Имена файлов обязательно указываем **с расширениями** и **не «теряем» пробелы**.
*   Помним, что Git управляет сохраненными файлами, а не теми, что в процессе редактирования.
*   Работать с Git можно двумя способами:
    1.  Через командную строку (терминал).
    2.  Через IDE (например, VS Code).

## Ветки (Branching)

Работу с ветками начинаем с запуска Git в репозитории.
*   Вводим `git init` и `git status`, чтобы убедиться, что репозиторий создан.
*   Повторяем команды `git add`, `git log`, `git status`.

**Создать ветку** можно командой:
`git branch <название новой ветки>`
*Делать это надо в папке с репозиторием.*

**Переключение между ветками:**
Во время лекции у нас была ветка `master` с черновиком и отдельная ветка — с читовиком. Если потребуется переключиться с одной ветки на другую, вводим:
`git checkout <имя>`

**Просмотр истории:**
Команда `git log` покажет состояние более новых версий проекта. Но если вызвать эту команду из самой «свежей» ветки, мы не увидим исходного файла.
*   Когда мы правим текст/код в текущей ветке, автоматического слияния не происходит: можно создать один документ в разных версиях в разных ветках.

## Слияние (Merge)

Допустим, черновик нас полностью устраивает и нам нужно внести изменения, чтобы информация появилась в читовике. Для этого есть команда `git merge`.

**Как выполнить слияние:**
Чтобы слить любую ветку с текущей, вызываем:
`git merge <имя ветки для слияния с текущей>`

### Схема работы с ветками (из изображения):
1.  **initial commit** (начальный коммит)
2.  **Задали структуру документа**
3.  **Добавили инструкции по выделению курсивом и полужирным**
4.  **Добавили альтернативный вариант курсива и полужирного**
5.  **Указали как совмещать 2 варианта текста**
    *   Ветка `text_formatting` сливается с веткой `master`.
    *   Ветка `lists` (Добавили нумерованные и ненумерованные списки) идет параллельно.

*Если ветка `text formatting` больше не нужна, ее можно удалить.*

## Игнорирование файлов

В Git не принято добавлять файлы изображений, их хранят на сторонних хостингах.
Чтобы исключить ненужные файлы из загрузки, есть команда `git ignore`.

## Конфликты и их разрешение

При работе в двух ветках одновременно может возникнуть ситуация, когда в одной и другой ветке мы по-разному изменили блок текста.
*   Если затем мы попробуем слить эти ветки, Git сообщит о **конфликте** и предложит выбрать, какие же изменения записать.

**Важное правило:**
Поэтому у проекта в репозитории должен быть **один ответственный пользователь**, наделённый правом проводить слияния и разрешать конфликты.

## Полезная команда для визуализации

`git log --graph` — ключ `--graph` в связке с командой `log` позволяет отобразить коммиты в виде дерева.



## Команда git clone

Команда `git clone` составная:
она не только загружает все изменения, но и пытается слить все ветки на локальном компьютере и в удаленном репозитории.

## git pull

Эта команда позволяет скачать все из текущего репозитория и автоматически сделать merge с нашей версией.

## git push

Отправить свою версию репозитория во внешний репозиторий поможет команда `git push`. При первом её использовании нужна `git pull` авторизация. Эта команда позволяет отправить нашу версию репозитория на внешний репозиторий. **ТРЕБУЕТ АВТОРИЗАЦИИ** на внешнем репозитории.

## Как сделать pull request

1.  Делаем (ответвление) репозитория **fork**
2.  Делаем `git clone` версии репозитория **СВОЕЙ**
3.  Создаем новую ветку и в **НЕЕ** вносим свои изменения
4.  Фиксируем изменения (делаем коммиты)
5.  Отправляем свою версию в свой GitHub
6.  На сайте GitHub нажимаем кнопку **pull request**
